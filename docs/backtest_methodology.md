# 백테스트 방법론 (지시서 §55·§56·§57·§71·§72·§74)

> 마지막 갱신 2026-08-31 · Phase 8

이 문서는 "우리 모델이 몇 점이었나" 를 적은 성적표가 아니다.
**"그 점수를 믿어도 되는가"** 를 판정하는 규칙을 적은 문서다.

---

## 0. 왜 이렇게까지 하는가

백테스트는 거의 항상 좋게 나온다. 그리고 거의 항상 틀린다.
이유는 셋이고, 셋 다 사람이 조심해서는 못 막는다.

| 실패 방식 | 어떻게 생기나 | 여기서 막는 방법 |
|---|---|---|
| Look-ahead | 그 시점에 몰랐던 데이터가 모델에 들어간다 | 컷오프 guard + 정답지 격리 + 미래삭제 비교 |
| In-sample 과적합 | 같은 구간에서 배우고 같은 구간을 채점한다 | 시간 분할(§72) + walk-forward |
| 표본 부풀리기 | 겹친 창을 독립 관측으로 센다 | 유효표본(겹치지 않는 창 수) + t 검정 |

세 번째는 특히 눈에 안 띈다. 3개월 간격으로 2년 보유를 채점하면 창 하나가
뒤따르는 8개 창과 같은 기간을 채점한다. 창 36개를 "표본 36" 으로 쓰면
신뢰도를 8배 부풀린 것이다. 실제로 **신호를 0 으로 넣은 합성 시장에서
IC +0.13 짜리 "유용한 feature" 가 만들어지는 것을 관측했다.**

## 1. 창 만들기 (walk-forward)

```
as_of 2018-01  ─ 결정 ─▶            2020-01 채점  (2년)
as_of 2018-07  ─ 결정 ─▶            2020-07 채점
as_of 2019-01  ─ 결정 ─▶            2021-01 채점
  …
```

각 창은 자기보다 앞선 데이터만 본다. 채점 결과는 그 창의 결정에 영향을 주지
않는다.

* 채점 시점이 데이터 끝을 넘는 창은 **버리지 않고** `PENDING` 으로 남긴다.
  "왜 창이 이것밖에 없나" 에 답할 수 있어야 한다.
* 초반 `warmup_months`(기본 12개월) 는 창을 만들지 않는다. momentum·regime 을
  계산할 과거가 없어서 "데이터 부족" 만 나온다.

## 2. 분할 (§72)

```
├──────── TRAIN ────────┤── VALIDATION ──┤──── OOT ────┤
```

**시간으로** 자른다. 무작위 분할은 2021년 데이터로 2019년을 맞히는 것이라
성적이 부풀려지고 실전에서 재현되지 않는다.

### 2-1. 숨은 함정 — 정답 구간의 침범

시간으로 잘라도 문제가 남는다.

```
TRAIN  as_of 2021-07 ─ 5년 정답 ─▶ 2026-07
VALID  as_of 2022-01  ← 이 시점의 시장을 TRAIN 의 정답이 이미 알고 있다
```

학습 표본의 **정답 구간**이 검증 구간을 덮으면 검증은 더 이상 독립이 아니다.
자동으로 잘라내지 않는다 — horizon 이 길면 겹침은 불가피하고 무엇을 버릴지는
실험 설계다. 대신 **몇 개가 겹치는지 항상 보고한다**(`embargo_conflicts`).
잘라내고 싶으면 `--purge`.

### 2-2. 검정력을 미리 본다

`backtest plan` 이 돌리기 **전에** 알려준다.

```
TRAIN 2년: 창 46개 · 독립 관측 6개 · 충분
VALIDATION 2년: 창 15개 · 독립 관측 2개 · 부족 — 3개 필요
→ VALIDATION 에서 2년 보유를 검증하려면 6년짜리 구간이 필요합니다
```

**이것이 지금 이 프로젝트의 가장 큰 제약이다.**
2년 보유를 검증하려면 겹치지 않는 창 3개 = **6년짜리 검증 구간**이 필요하다.
5년 보유면 15년, 10년 보유면 30년이 필요하다.

| 보유기간 | 검증에 필요한 구간 | 60/20/20 기준 필요한 전체 데이터 |
|---:|---:|---:|
| 2년 | 6년 | 30년 |
| 5년 | 15년 | 75년 |
| 10년 | 30년 | 150년 |

국토부 실거래 공개는 2006년부터다. 즉 **5년·10년 랭킹의 가중치는 정식으로
검증할 수 없다.** 학습 비율을 줄여(`--train-frac 0.45 --val-frac 0.35`) 2년은
검증할 수 있고, 5년 이상은 TRAIN IC 까지만 보고 가중치는 heuristic 을 유지한다.
이 사실을 감추지 않고 리포트에 표시한다.

## 3. 정답 계산 (§33·§34·§36·§40·§41)

정답은 **후보 전체** 에 대해 계산한다. 우리가 고른 것만 채점하면
Regret 도 Missed Winner 도 계산할 수 없다 — 놓친 것을 봐야 놓친 걸 안다.

| 값 | 규칙 |
|---|---|
| 진입가·청산가 | 목표 월 ±3개월 안에 실제 스냅샷이 있어야 한다. **보간하지 않는다** |
| forward_return | (청산가 − 진입가) / 진입가 |
| max_drawdown | 시작가가 아니라 **보유 중 고점** 대비 |
| recovery_months | 저점에서 직전 고점 회복까지. 회복 못 했으면 `(None, False)` — "모른다(None, None)" 와 다르다 |
| rise_start_ym | 3개월 이상 지속된 5% 상승의 시작 달. Discovery Lag 의 기준점 |

값을 못 내면 0 이나 평균으로 채우지 않고 `unknown_reason` 을 남긴다.
스키마 CHECK 가 이걸 강제한다 — 사유 없는 결측은 INSERT 자체가 실패한다.

### Winner 4상태 (§41)

|  | 실제로 좋았다 (상위 20%) | 아니었다 |
|---|---|---|
| **골랐다** | WINNER_FOUND | FALSE_POSITIVE |
| **안 골랐다** | MISSED_WINNER | CORRECT_REJECT |

Winner 기준은 **동시점 후보 상위 20%** 다. 절대 수익률이 아니라 상대 기준이라
하락장에서도 정의된다(§56).

## 4. KPI 14종 (§57)

| KPI | 무엇을 잡아내는가 |
|---|---|
| winner_recall_at_k | 진짜 좋았던 것을 몇 개나 찾았나 |
| precision_at_k | 우리가 고른 것 중 몇 개가 진짜였나 |
| false_positive_rate | 자신 있게 골랐는데 아니었던 비율 |
| false_follower_rate | "따라 오를 것" 이라고 봤는데 시장에도 못 미친 비율 |
| regret | 그때 살 수 있었던 최선 대비 손해 |
| opportunity_alpha | 그냥 아무거나 산 것(중앙값)보다 나았나 |
| ex_post_capital_rank | 사후에 보니 우리 1위가 실제 몇 위였나 |
| median_forward_return | 고른 것들의 실현 수익률 중앙값 |
| hit_rate | 시장 중앙값을 이긴 비율 |
| rank_ic | 점수 순서와 실제 성과 순서가 맞았나 |
| max_drawdown | 보유 중 최대 낙폭 |
| recovery_months | 저점에서 회복까지 |
| discovery_lag | 상승이 시작되고 몇 달 뒤에 찾았나 |
| coverage | 후보 중 정답을 계산할 수 있었던 비율 |

* **표본이 없으면 값을 만들지 않는다.** 스키마가 `value IS NULL OR sample_n > 0`
  을 강제한다 — 표본 0개로 낸 정확도 100% 는 성적이 아니다.
* 창끼리 겹치므로 집계는 표본을 더하지 않고 **창 중앙값**을 쓴다.

## 5. Feature usefulness → Weight (§74)

```
데이터 → Feature → Backtest → Feature usefulness → Weight → Ranking
                               ~~~~~~~~~~~~~~~~~~~~~~~~~~
```

### 판정 기준

USEFUL 이 되려면 **넷을 전부** 통과해야 한다.

1. 겹치지 않는 창 3개 이상 (유효표본)
2. IC 중앙값 ≥ 0.05
3. **t = |IC| / (창별 IC 표준편차 ÷ √유효표본) ≥ 2.0**
4. 방향이 같은 창이 60% 이상

그리고 VALIDATION 에서 **부호가 같고 기준을 넘어야** 확인된다.

3번이 핵심이다. 임계값 하나(IC ≥ 0.05)만 두면 유효표본 4~6개에서
표준오차가 0.09~0.12라 +0.07 같은 잡음이 통과한다. 신호를 0 으로 넣은
합성 시장에서 실제로 그렇게 통과하는 것을 보고 추가했다.

### 확인되지 않으면 학습하지 않는다

VALIDATION 을 통과한 모델이 하나도 없으면 **가중치를 만들지 않고**
heuristic 을 그대로 쓴다. 근거 없는 숫자가 "학습됨" 라벨을 다는 것이
임시 가중치를 임시라고 부르는 것보다 위험하다.

### 기존 생각을 버린다

heuristic 이 10% 이상 줬던 모델이 0 이 되면 그 사실을 문장으로 남긴다.

```
heuristic 이 20% 를 줬던 'value' 의 가중치를 0 으로 내렸습니다
— VALIDATION 확인됨 (IC -0.509). (§74: 백테스트가 기존 생각과 다르면 기존 생각을 버린다)
```

## 6. 누출 방지 — 세 겹 (§18·§55·§69)

| 겹 | 무엇을 막나 | 한계 |
|---|---|---|
| ① 구조 | 컷오프 없는 조회를 SQL 단계에서 거부 | 파이썬 쪽 날짜 비교는 못 본다 |
| ② 정적 | 결정 경로 코드가 정답지를 언급하는지 AST 검사 | 이름을 조립하면 피해간다 |
| ③ 경험적 | **미래를 실제로 지운 DB** 로 같은 결정을 다시 내려 비교 | 우회 방법이 없다 |

③이 가장 강하다. 결과가 달라지면 어딘가에서 미래를 본 것이고, 그건 사실 자체다.

### 정답지 격리

`backtest_outcome` · `backtest_kpi` · `feature_usefulness` · `weight_fit` 은
`ANSWER_KEY_TABLES` 에 등록돼 있어서, 컷오프 guard 안에서는 **어떤 조건을
붙여도** 읽을 수 없다. 채점 코드는 guard 밖에서 돈다.

### 검사가 진짜로 작동하는지 검사한다

`tests/test_backtest.py::test_미래를_심으면_잡는다` 가 컷오프 이후 가격을
일부러 3배로 부풀리고, 그걸 읽는 코드를 누출 검사가 잡아내는지 확인한다.
**이 테스트가 실패하면 누출 검사는 아무 것도 보장하지 않는다.**

### 누출이 발견되면 무효

`backtest_run` 에 CHECK 가 있다.

```sql
CHECK (status != 'COMPLETE' OR (leakage_checked = 1 AND leakage_found = 0))
```

성적을 먼저 보고 나서 누출을 찾으면 사람은 좋았던 실행을 살리고 싶어진다.
그래서 코드가 아니라 스키마로 막았다.

## 7. 합성 시장 (하네스 검증용)

실거래 데이터가 오기 전까지 하네스가 실제로 도는지 확인해야 한다.
그러려면 **정답을 이미 아는 시장**이 필요하다.

| 규칙 | 심어 놓은 것 | 기대 결과 |
|---|---|---|
| MOMENTUM | 오르던 단지가 계속 오른다 | momentum 이 가중치를 받는다 |
| MEAN_REVERT | 지역 평균보다 싼 단지가 되돌아온다 | **반대로** value 가 받는다 |
| NONE | 아무 규칙도 없다 | 아무것도 학습하지 않는다 |

**같은 코드가 시장에 따라 다른 답을 내야 한다.** 항상 같은 답이 나오면
데이터를 읽는 게 아니라 미리 정해 둔 답을 되풀이하는 것이다.
`test_시장이_바뀌면_학습_결과도_바뀐다` 가 이걸 확인한다.

합성 데이터는 실제 DB 파일에 쓸 수 없다(`require_scratch()` 가 막는다).
합성으로 학습한 가중치는 `market_source='SYNTHETIC'` 로 저장되고,
실전 랭킹은 `REAL` 만 읽는다.

## 8. 쓰는 법

```bash
# 이 설계로 학습이 가능하기는 한지 먼저 본다
apt backtest plan --start 2006-01-01 --end 2026-01-01 --horizon 2 --step 3

# 검정력이 모자라면 학습 비율을 줄여 검증 구간을 늘린다
apt backtest plan ... --train-frac 0.45 --val-frac 0.35

# 돌린다
apt backtest run --start 2006-01-01 --end 2026-01-01 \
    --horizon 2 --step 3 --run-key wf1

# 학습 결과를 본다
apt backtest weights --run-key wf1

# 학습된 가중치로 랭킹을 낸다 (없으면 heuristic 으로 돌아가고 그 사실을 표시)
apt rank --cash 3 --horizon 2 --weights backtested
```

## 9. 지금 상태

실거래 데이터가 **0건**이라 위 전 과정을 합성 시장으로만 검증했다.
따라서 지금 나오는 KPI 는 **성적이 아니라 배관 검증 결과**다.

수집이 끝나면 순서는 이렇다.

1. `backtest plan` 으로 검정력 확인 → 어떤 horizon 을 검증할 수 있는지 결정
2. `backtest run` → KPI + Feature usefulness
3. `backtest weights` → 학습된 가중치 확인
4. `rank --weights backtested` → 그때부터 "임시(heuristic)" 딱지가 사라진다
