# 촉매(호재) 엔진 (지시서 §77·§17·§18·§34)

> 마지막 갱신 2026-08-31

---

## 0. 가장 중요한 것 — 서사에 점수를 주지 않는다

§49-9 가 금지한 것:

> 재건축 / GTX 등 Narrative 에 고정점수 부여 금지.

"GTX 예정 → +10점" 이 틀린 이유는 둘이다.

```
① 그 기대가 이미 가격에 얼마나 들어갔는지를 안 본다
② 실현되면 얼마를 버는지를 안 본다
```

같은 "GTX 호재" 라도 이미 30% 반영됐으면 남은 게 크고, 90% 반영됐으면
살 이유가 없다. 고정점수는 이 둘을 구분하지 못한다.

## 1. 다섯 요소가 **전부** 있어야 알파가 나온다

```
CatalystAlpha = 실현확률 × 경제효과 × (1 − 선반영률) × 노출도 × 시간적합성
```

하나라도 없으면 **점수를 만들지 않는다**(`alpha_of()` 가 `None` 을 돌려준다).
넷을 알고 하나를 모르면 그건 "80% 아는 것" 이 아니라 "모르는 것" 이다.

| 요소 | 뜻 | 없으면 |
|---|---|---|
| 실현확률 | 이 사업이 실제로 될 확률 | 알파 없음 |
| 경제효과 | 되면 만드는 가치 (원) | 〃 |
| 선반영률 | 이미 가격에 들어간 비율 | 〃 |
| 노출도 | 이 단지가 얼마나 혜택 받나 | 〃 |
| 시간적합성 | 내 보유기간 안에 일어나나 | 〃 |

시간적합성은 보유기간 안이면 1.0, 넘어가면 `max(0.1, 1/(1+초과연수))` 다.
10년 뒤 개통을 2년 투자에 넣으면 거의 0 이 된다.

## 3. 시점별 원장 (§18)

이게 look-ahead 방지의 핵심이다.

```
catalyst          호재 자체 (시점 개념 없음)
catalyst_state    그 시점의 상태 (as_of 마다 한 행)
catalyst_exposure 그 시점의 단지별 노출도
```

**과거 상태를 덮어쓰지 않는다.** 2019년에 "계획" 이었던 것이 2023년에
"착공" 이 됐으면 두 행이 된다. 2019년 시점 백테스트는 "계획" 행만 본다.

그리고 Catalyst Vintage 네 날짜를 따로 갖는다(§30).

```
announcement_date · confirmation_date · construction_date
· expected_completion · actual_completion
```

§18 이 금지한 것: **미래에 실제 개통된 사실을 과거 모델이 알고 있었던 것처럼
사용하지 마라.**

## 4. 전달경로 (§34)

호재가 가격을 올리는 길은 넷뿐이다.

| 경로 | 질문 |
|---|---|
| BuyerPool | 이 호재로 이 단지를 살 수 있는 사람이 늘어나는가 |
| Accessibility | 일자리·중심지 접근이 좋아지는가 |
| PriceLadder | 생활권 내 서열이 올라가는가 |
| EffectiveSupply | 경쟁 공급이 늘거나 주는가 |

**어느 경로로도 설명이 안 되면 점수가 없다.** 그리고 설명된 경로가 적을수록
점수가 낮다(커버리지를 곱한다).

이게 "GTX 니까 좋다" 를 "이 호재로 강남 접근이 20분 빨라지고, 그러면 이
가격대를 살 사람이 늘어난다" 로 바꾸는 장치다.

## 5. 지금 상태

`catalyst` · `catalyst_state` 가 **비어 있다.** 교통사업 단계는 수기 입력이다.

```bash
apt transit template rules/transit.csv
apt transit import rules/transit.csv
apt catalyst ...
```

없으면 `catalyst_alpha` 가 "확인 불가" 이고, Consensus 의 `catalyst` 모델이
가중치에서 빠진다(0점 처리가 아니다).
