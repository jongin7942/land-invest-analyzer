> 마지막 갱신 2026-08-31

---

## 1. 무엇을 Carbon 에서 가져오고 무엇을 우리가 정하는가

| Carbon 에서 | 우리가 |
|---|---|
| 토큰 구조 (`$layer-01`, `$text-primary` …) | **색 전부** |
| 간격 스케일 (`$spacing-01`~`09`) | 한글 폰트 (Pretendard) |
| 타이포 스케일 | 상승/하락 방향 (한국 관행) |
| 그리드·브레이크포인트 | 데이터 등급 표시 규칙 |
| 컴포넌트 마크업·동작·접근성 | 화면 구성 |

**IBM 로고·상표·고유 문구는 쓰지 않습니다.**
Carbon 은 오픈소스 디자인 시스템이고, 우리가 쓰는 것은 그 구조입니다.

## 2. 패키지 — 왜 `@carbon/react` 가 아닌가

이 앱은 **Flask + Jinja2 서버 렌더링**입니다. React 앱이 아닙니다.

| 패키지 | 버전 | 씀? |
|---|---|---|
| `@carbon/styles` | 1.114.0 | ✅ 실제 컴포넌트 CSS + 토큰 |
| `@carbon/web-components` | 2.62.0 | 설치만 — 아래 참조 |
| `@carbon/react` | — | ❌ 프론트를 React 로 재작성해야 함 |

### web-components 를 설치하고도 안 싣는 이유

번들이 **1.2MB(gzip 139KB)** 입니다. 그런데 지금 화면에서 클라이언트 JS 가
필요한 곳이 없습니다.

| 요소 | 어떻게 |
|---|---|
| 보기 모드 전환 | 링크 (`?mode=easy\|expert`) — 서버 렌더 |
| 탭 | 링크 |
| 근거 펼치기 | 네이티브 `<details>` |
| 버튼·입력·태그·알림·스켈레톤 | **Carbon CSS 클래스** (`cds--btn` 등) |

아무 동작도 없는 페이지에 139KB 를 싣는 것은 느린 회선의 사용자에게
값을 치르게 하는 일입니다. 지도처럼 진짜로 JS 가 필요한 화면이 생기면
그때 `npm run build:js` 로 붙입니다 — 패키지는 이미 설치돼 있습니다.

```
static/css/app.css   391KB (gzip 37KB)   ← 지금 싣는 것
static/js/carbon.js  1.2MB (gzip 139KB)  ← 필요할 때만
```

## 3. 색

Carbon 의 IBM Blue(#0f62fe)를 쓰지 않습니다. 그대로 쓰면
"IBM 처럼 생긴 화면" 이 됩니다.

### 핵심색 — 짙은 남색

`styles/_brand.scss` 의 `$brand-700: #16365e` 가 기본 액션입니다.
흰 배경 대비 **9.1:1** — Carbon 의 본문 기준(4.5:1)을 넉넉히 넘습니다.

금융기관에서 오래 쓰인 색이라 신뢰로 읽히고, 부동산 화면의 빨강/파랑
(상승/하락)과 겹치지 않습니다.

### 상승 빨강 · 하락 파랑

미국식(상승 초록)과 반대입니다. 국내 사용자가 매일 보는 방향으로 맞췄습니다.

```scss
$rise-500: #c62828;   // 상승 (대비 5.9:1)
$fall-500: #1565c0;   // 하락 (대비 5.6:1)
```

**⚠ 색만으로 구분하지 않습니다.** `.delta--up` / `.delta--down` 이
`::before` 로 **▲ ▼** 를 항상 붙입니다. 색각 이상인 사람에게 빨강·파랑은
구분이 어렵습니다. 이건 선택이 아니라 Carbon 접근성 기준입니다.

## 4. 데이터 등급 (§5) — 절대 섞지 않는다

```
.grade--confirmed   실거래   초록   실제로 일어난 거래
.grade--listing     호가     주황   파는 사람이 부르는 값
.grade--estimated   추정     회색   우리가 만든 값
.grade--unknown     확인불가 빨강   0 이 아니다
```

실거래가와 매물호가를 하나의 가격처럼 합치지 않습니다. 색과 라벨 **둘 다**
로 구분합니다.

모든 숫자 아래에 `.provenance` 로 출처·기준일이 붙습니다.

---

## 5. 점수 (§6) — 종합점수만 크게 보여주지 않는다

`.score-set` 은 항상 세 값을 나란히 둡니다.

```
Expected Alpha  78     Risk  42     Confidence  83
```

Alpha 78 / Confidence 30 은 Alpha 40 과 **완전히 다른 상태**입니다.
하나로 합치면 그 구분이 사라집니다.

그 아래 `.factor-list` 가 점수를 올린/내린 요인을 가중치와 함께 보여주고,
`<details class="evidence">` 를 펼치면 산식과 원본 데이터가 나옵니다.

## 화면 구성 (2026-09 전환 완료)

| 경로 | 화면 | 하는 일 |
|---|---|---|
| `/` | 순위 | 투자금 → 실행가능 후보. 학습 전에는 **잠김** |
| `/search` | 단지 검색 | 이름으로 찾고 비교 후보로 담기 |
| `/compare` | 종합 비교 | 담아둔 단지 최대 5개를 항목별로 가로 비교 |
| `/conclusion` | 최종 투자결론 | ① 살 수 있는가 ② 어느 것이 나은가 ③ 사지 않는 선택 |
| `/complex/<id>` | 단지 상세분석 | 대표가격 · 실투자금 · 산식 펼치기 |
| `/status` | 데이터 현황 | 수집·매칭·규칙 입력 상태 |
| `/unmatched` | 미매칭 | 실거래에 있는데 못 붙인 이름 |

### 비교 후보를 쿠키에 두는 이유

DB 커넥션이 읽기 전용이다(`ro_conn`). 수집 배치가 쓰기 트랜잭션을 오래
잡기 때문에 일반 커넥션으로 열면 화면이 `database is locked` 로 죽는다.
서버에 쓸 수 없고, 담아둔 후보는 개인 설정이라 서버에 둘 이유도 없다.

최대 5개인 이유는 가로 비교표가 그 이상에서 읽히지 않기 때문이다 —
화면에 다 안 들어가고, 사람이 한 번에 비교할 수 있는 항목 수도 그쯤에서 끝난다.

### 비교 화면이 지키는 규칙

**새 산식을 만들지 않는다.** 비교표의 필요 현금은 단지 상세화면과
같은 `cash.self_capital.compute` 를 같은 인자로 부른 결과다. 화면마다
다른 값이 나오면 둘 중 하나는 틀린 것이고, 사용자는 어느 쪽이 틀렸는지
알 방법이 없다.

**하한값끼리 1등을 뽑지 않는다.** 확인 불가 항목이 있으면 필요 현금은
"이 정도 이상" 이다. 하한끼리 대소를 따지면 **못 구한 비용이 큰 단지가
가장 싸 보인다.** `_best()` 는 `unknown` 이 있는 행을 비교에서 뺀다.

**면적대를 섞지 않는다.** 같은 단지 안에서도 면적대가 다르면 다른
상품이다. 고른 면적대를 표에 반드시 표시하고, 단지마다 다르면 경고를 띄운다.

### 결론 화면이 지키는 규칙 (§12)

지금 데이터로 정직하게 말할 수 있는 것은 두 가지뿐이다.

1. **가진 현금으로 실제로 살 수 있는가** — 규칙만 있으면 사실 판정
2. **그중 어느 것이 더 좋은가** — 가중치를 학습해야 답할 수 있다

②를 못 하는 동안 ①을 ②인 것처럼 보여주지 않는다. 결론 화면은
**자기 점수를 만들지 않는다** — 순위는 순위 화면 한 곳에서만 나온다.

확인 불가 항목이 하나라도 있으면 "살 수 있음" 이라고 말하지 않는다.
못 구한 비용을 0원으로 세면 실제로는 못 사는 집이 살 수 있는 집으로 보인다.

### 화면 회귀 테스트

`tests/test_ui_screens.py` (27개). 색이나 여백이 바뀌는 것은 상관없고,
**표시 규칙**이 깨지면 테스트가 깨진다 — 못 구한 값이 0 으로 찍히는지,
하한값에 "이상" 이 붙는지, 실거래와 호가가 섞이는지, 빈 화면이 다음
행동을 주는지, 열린 리다이렉트가 막히는지.

## Carbon 을 실제로 적용할 때 걸린 두 가지

브라우저로 렌더해 보기 전까지 **CSS 는 빌드되는데 화면은 Carbon 이 아닌**
상태였다. 둘 다 조용히 실패해서 SCSS 만 봐서는 알 수 없었다.

### ① 버튼·입력이 납작하게 나왔다 — `scss/layout` 누락

Carbon 의 버튼과 입력은 높이와 좌우 패딩을 전부
`var(--cds-layout-size-height-lg)` 같은 커스텀 프로퍼티로 계산한다.
그 변수를 `:root` 에 발행하는 것이 `@carbon/styles/scss/layout` 이다.
컴포넌트 CSS 만 가져오면 계산식은 멀쩡한데 변수가 비어 있어서
`padding` 이 0 이 되고, 버튼이 글자 크기 그대로 나온다.

### ② 화면이 IBM 파랑으로 나왔다 — 테마를 발행하지 않았다

`@use '@carbon/styles/scss/theme' with ($theme: (...))` 는 **Sass 변수만**
바꾼다. 컴포넌트 CSS 는 `var(--cds-button-primary, #0f62fe)` 처럼
**커스텀 프로퍼티 + IBM 색 폴백**으로 쓰기 때문에, `:root` 에
`@include theme.theme()` 를 넣지 않으면 폴백이 이긴다.

여기에 더해 `theme()` 는 **기본 테마 → 컴포넌트 토큰** 순으로 발행하는데,
`button-*` 과 `notification-background-*` 는 컴포넌트 토큰 층에 있어서
`$theme` 맵에 적어도 뒤에서 IBM 기본색으로 다시 칠해진다. 그 10개만
`app.scss` 끝에서 한 번 더 못박는다.

### 체크박스는 네이티브를 쓴다

Carbon 1.x 의 checkbox SCSS 는 상자 그림을 웹컴포넌트 쪽에 두고 있어
순수 HTML 로는 네모가 안 그려진다. 네이티브 체크박스에 `accent-color`
만 브랜드색으로 주고 라벨 타이포만 Carbon 것을 얹었다 — 네이티브가
접근성과 조작성이 더 낫고, 이걸 위해 1.2MB 웹컴포넌트 번들을 실을 이유가 없다.

## 반응형 검증 (Playwright)

PC 1440px · 모바일 390px 두 폭에서 6개 화면을 렌더해 확인한다.

- **페이지 본문은 절대 가로로 밀리지 않는다** (`scrollWidth - clientWidth == 0`).
  넘치는 표는 `.table-scroll` / `.compare-scroll` **안에서만** 스크롤한다.
- 모바일에서 표는 짜부라지는 대신 스크롤한다 (`min-width: 620px`).
  열이 좁아지면 글자가 한 자씩 끊기고 오른쪽 열은 잘려 나간다.
- 비교표는 모바일에서 가로표 → **항목별 세로 카드**로 바뀐다
  (`td::before { content: attr(data-label) }` 로 어느 단지 값인지 붙인다).
- 상단 메뉴는 모바일에서 **아랫줄로 내린다.** 한 줄에 두면 서비스명과
  보기모드에 밀려 40px 만 남고, 가로 스크롤이 걸려도 사용자는 거기
  메뉴가 더 있는 줄 모른다.

## 타이포 — 한글 기준으로 다시 잡은 것

Carbon 의 productive 스케일은 **영문 UI 기준**이다. 그대로 쓰니 세 가지가
동시에 걸렸다.

| | Carbon 기본 | 우리 값 | 왜 |
|---|---|---|---|
| `body-01` | 14px / 1.43 | **16px / 1.75** | 본문 |
| `body-compact-01` | 14px / **1.29** | **15px / 1.65** | 표·목록. 1.29 는 한글 줄이 서로 붙는다 |
| `label-01` | **12px** | **13px / 1.6** | 출처·기준일·신뢰도가 전부 이 크기다 |
| `letter-spacing` | 0.16px | **0** | 라틴용 트래킹. 한글에 주면 초점이 안 맞는다 |
| 제목 굵기 | 300~400 | **600~700** | 큰 제목이 얇으면 한글은 획이 가늘어 흐려진다 |
| `productive-heading-05` | 32px | **28px** | 크기를 줄이고 굵기를 올리는 쪽이 더 잘 읽힌다 |

한글은 같은 픽셀에서 라틴 문자보다 작아 보인다 — 가로획이 많아 자소가
뭉치기 때문이다. 그래서 크기는 올리고 자간은 0 으로 되돌린다.

Carbon 은 타입을 `var(--cds-body-01-font-size, …)` 로 발행하므로
**토큰만 다시 정의하면** 200개 넘는 호출부를 안 건드리고 전부 바뀐다.
`app/_type.scss` 를 믹스인으로 둔 이유는 색과 같다 — Carbon 타입 모듈도
`:root` 에 같은 토큰을 발행해서, 우리 것이 **뒤에** 나와야 이긴다.

### 숫자에서 IBM Plex Mono 를 뺐다

자릿수는 잘 맞았지만 화면이 **터미널 출력처럼** 보였다. "9.78억" 이
코드로 읽힌다. Pretendard 에도 고정폭 숫자가 들어 있어서
`font-variant-numeric: tabular-nums` 만 켜면 자릿수는 그대로 맞으면서
본문과 같은 얼굴로 읽힌다. 비교표에서 숫자가 흔들리지 않는 것이
목적이었지 고정폭 폰트를 쓰는 것이 목적이 아니었다.

Plex Mono 는 `.formula` 와 `<code>` — **실제 코드**에만 남겼다.

### 금액은 '억' 으로 읽고 '원' 으로 확인한다

`900,000,000원` 은 자릿수를 세어야 읽힌다. 사람은 "9억" 으로 읽는다.
그렇다고 억만 보여주면 반올림된 값이 유일한 값이 되므로,
`ui.money()` 매크로가 둘을 나란히 둔다 — 읽는 값과 확인하는 값.

큰 크기는 `.metric__value` 안, 즉 **그 화면의 답일 때만** 준다.
표 안에서 키우면 그 칸이 가장 중요한 값처럼 읽히는데 표에서는
어느 칸도 그렇지 않다.

### 글의 배치

- 본문 한 줄은 `74ch`, 안내문은 `66ch` 에서 끊는다. 줄이 길면 다음 줄
  첫 글자를 못 찾는다.
- `word-break: keep-all` — 한글은 단어 중간에서 끊지 않는다.
- 제목 **위** 여백은 넉넉히, 제목과 그 아래 내용 사이는 좁게.
  그래야 어떤 제목에 딸린 내용인지 눈으로 바로 묶인다.
- 본문 최대 폭을 1584px → **1200px**. 1584 는 Carbon 의 최대 그리드 폭이지
  읽기 좋은 폭이 아니다 — 그 폭에서는 표의 왼쪽 항목과 오른쪽 값이
  너무 멀어져 눈이 한 줄로 못 묶는다.

## 대시보드 레이아웃 (목업 반영)

가로 메뉴 → **왼쪽 세로 메뉴 + 상단 바 + 오른쪽 패널** 구조로 바꿨다.

```
┌────────┬──────────────────────────────────────────────┐
│ 메뉴   │ 상단 바  제목 · 데이터 기준일 · 보기 모드      │
│ (216)  ├──────────────────────────────────────────────┤
│        │ 나의 투자 조건 (투자금 · 주택수 · 보유기간)    │
│ 투자처 │ 요약 지표 4개                                │
│ 비교   ├──────────────────────────┬───────────────────┤
│ 검색   │ 순위표 (9열)             │ 왜 1위인가요?     │
│ 결론   │                          │  핵심 투자 논리   │
│ 현황   │                          │  추천 매수가      │
│ 미매칭 │                          │  가장 큰 위험     │
│        │                          │  추이 차트        │
│ 접기   │                          │  상세 분석 보기   │
└────────┴──────────────────────────┴───────────────────┘
```

- 세로 메뉴로 옮긴 이유: 화면이 늘어날수록 가로 메뉴는 이름을 줄여야 한다.
  세로는 이름을 온전히 쓰면서 아이콘으로 위치를 기억시킨다.
- **모바일은 아래쪽 탭바**로 바뀐다. 세로 메뉴를 그대로 두면 폭의 절반을 먹고,
  엄지가 닿는 곳에 있어야 한 손으로 쓸 수 있다.
- 아이콘은 **인라인 SVG**(`templates/_icons.html`). 아이콘 폰트나 CDN 을 쓰면
  네트워크가 없을 때 네모로 남는다. 이 앱은 로컬에서 돈다.
- 추이 차트도 **SVG 를 직접 그린다.** 선 두 개에 차트 라이브러리 100KB 를
  받을 이유가 없다. y축을 0 에서 시작하지 않는 대신 **눈금에 실제 값을 적어**
  기울기만 보고 오해하지 않게 한다.

### 순위표의 등급 열은 새 점수가 아니다

`저평가 / 상승 여력 / 하락 방어`는 이미 계산된 **모델 점수(value·momentum·
jeonse)를 말로 바꾼 것**이다. `_ratings()` 가 하는 일은 0.0~1.0 을 세 단계로
나누는 것뿐이고, 칸에 마우스를 올리면 원래 점수가 보인다. 여기서 새 산식을
만들면 상세화면 숫자와 표의 등급이 어긋나고, 사용자는 어느 쪽이 맞는지 알
방법이 없다.

`N년 세후수익` 열은 **비워 둔다.** 이 엔진은 세후 수익을 아직 내지 않는다.
추정치를 넣으면 그게 화면에서 가장 큰 숫자가 되어 전부를 좌우한다.

### `overflow-x: auto` 만으로는 부족했다

표는 스크롤 컨테이너 안에서 제대로 잘리는데(`clientWidth 366 / scrollWidth
1049`) **페이지 전체가 가로로 624px 스크롤됐다.** 오른쪽으로 스크롤하면
빈 배경만 나온다. 스크롤 컨테이너의 넘침 영역이 조상까지 전파된 것이다.

조상에 `overflow:hidden` 을 줘도 안 잡혔고, `contain: paint` 로 끊었다 —
"안쪽이 이 상자 밖으로 그려지지 않는다"는 뜻이라 의미도 정확히 맞는다.

그리드 칸에는 `min-width: 0` 이 따로 필요하다. 기본값 `auto` 는 min-content
라서 안쪽 표가 칸을 밀어낸다. 같은 이유로 `.stats` 의 `1fr` 도
`minmax(0, 1fr)` 이어야 한다 — `nowrap` 한 값이 칸을 넓혀 버린다.
