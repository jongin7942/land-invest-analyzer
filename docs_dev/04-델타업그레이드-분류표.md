240개월 중 27개월(11%), 남은 시간 약 27시간. 전월세는 아직 시작 전입니다.

* 제 실행환경은 data.go.kr이 차단돼 있어 **수집을 도울 수 없습니다.**
  그리고 수집 중 쓰기 명령은 락 충돌로 수집을 죽이므로(실제로 한 번 발생),
  이 세션에서는 실제 DB에 **쓰기를 일절 하지 않습니다.** 테스트는 임시 DB만 씁니다.

지시서 §49-3(미래 데이터 금지)과 최초 지시의 "LLM이 숫자를 추측하여 실제

## 이번 대조에서 **발견한 문제** — §45 중복 가산

지시서 §45가 "한 Feature를 여러 영역에서 중복 가산/감점하지 말라"고 했는데,
**지금 실제로 중복되고 있습니다.**

| Feature | ALPHA에서 | RISK에서 | 결과 |
|---|---|---|---|
| `entry_position` | `value` 모델의 **유일한** 입력 (낮을수록 가점) | `kill.상대고평가` (1.0 초과 배제) | 비쌀수록 alpha 감점 **+** 배제 — 이중 |
| `supply_ratio_1y` | `risk` 모델 입력 (낮을수록 가점) | — | |
| `supply_ratio_2y` | `supply` 모델 입력 | `kill.공급충격` | 이중 |
| `discovery_lag` | `momentum` 모델 (높을수록 감점) | `kill.급등후매수` | 이중 |
| `transaction_quality` | `risk` 모델 (높을수록 가점) | `kill.거래질악화` | 이중 |
| `flow_stage` | — | `kill.거래고점` | 단일 |
| `downside_defense` | `jeonse` 모델 | `kill.전세약화` | 이중 |

Kill이 **감점이 아니라 배제**라서 산술적 이중가산은 아니지만, 같은 신호가
순위와 생존 판정 양쪽을 움직이므로 **실질적으로는 가중치가 두 번 걸립니다.**
§45대로 Feature Attribution을 관리하려면 GATE/ALPHA/RISK 각 영역의 입력을
명시적으로 분리해야 합니다. 이번 업그레이드에서 고칠 항목으로 잡았습니다.

## STEP 4 — 최소변경 아키텍처 (기존 기능 안 깨는 방향)

원칙: **기존 19개 Feature와 7그룹을 지우지 않는다.** 4 State를 그 위에 얹는다.

```
                    ┌─ GATE ────────────────────────────────┐
                    │ Capital Feasibility · 규제 · 유동성    │  ← 기존 pipeline ②
                    │ Tradability · DataQuality 최소선       │
                    └───────────────────────────────────────┘
                                    ↓ 통과한 것만
  ┌─────────────── ALPHA ───────────────┐   ┌──── RISK ────┐
  │ CHEAPNESS   MOVEMENT   SUSTAIN      │   │ STRETCH      │  ← §4의 4 State
  └──────┬──────────┬──────────┬────────┘   └──────┬───────┘
         │          │          │                   │
    ┌────┴──────────┴──────────┴───────────────────┴────┐
    │  기존 7그룹 19 Feature (DIAGNOSTIC 으로 강등)       │  ← 삭제 안 함
    │  momentum · regime · flow · supply · jeonse ·      │
    │  entry · catalyst                                  │
    └────────────────────────────────────────────────────┘
                            ↓
              CORE Feature 10~20개 (§44)
              = 백테스트 여러 Fold 생존한 것만
```

`feature_usefulness` 테이블이 이미 Fold별 생존을 기록하므로, **§44의 CORE
축소는 새 메커니즘이 아니라 기존 테이블에 tier 컬럼 하나를 더하는 일**입니다.
