## ⚠ 먼저 — 이 PC에서 수집이 돌고 있습니다

```
python -m apt_engine.cli collect trades --months 240   ← 실행 중
```

**수집이 도는 동안 다른 쓰기 명령을 돌리지 마세요.** `snapshot` · `rule import` ·
`match` · `profile set` 전부 해당합니다.

실제로 한 번 사고가 났습니다. 수집 중에 `snapshot --months 6` 을 돌렸더니 스냅샷이
긴 쓰기 트랜잭션을 잡았고, 매매 수집이 `database is locked` 로 **죽었습니다.**
지금 코드는 락 충돌 시 재시도 없이 종료됩니다. 서울·경기 매매를 통째로 다시 받아야 했습니다.

읽기는 안전합니다. `apt_app.py`(UI)는 읽기 전용 커넥션이라 수집 중에도 씁니다.

## 이 세션에서 한 것

### 수집기 · 데이터 계층

- **K-apt 엔드포인트 확정** — 후보 URL 이 전부 폐기된 버전이었습니다.
  실제 동작: `AptListService4/getSigunguAptList4`, `AptBasisInfoServiceV5/getAphusBassInfoV5`.
  둘 다 JSON 만 주는데 파서가 XML 전용이라 정상 응답을 빈 목록으로 처리하고 있었습니다.
- **행정구역 코드 갱신** — 인천 개편(중구·동구 → 제물포/영종, 서구 → 서해/검단).
  그리고 `LEGACY`(과거 거래는 옛 통합코드로 조회) 가정이 **정반대**였습니다.
  실거래가 API 는 과거 데이터도 현재 코드로 소급 재편해서 줍니다. 폐지 코드는 전 기간 0건입니다.
- **단지명 매칭** — 표기 변형 계층 추가로 미매칭 49% → 26%.
  `부개주공3` ↔ `부개주공3단지`, `주공5`(부개동) ↔ `부개 주공5단지`, `동아(1차)` ↔ `부평 동아1단지`,
  `SK Sky VIEW` ↔ `에스케이스카이뷰`. WEAK 매칭은 3,117 → 224건.
- **`collect complexes` 트랜잭션 분할** — 전에는 전체가 트랜잭션 하나라 8천 호출 동안
  DB 가 잠기고 실패 시 통째로 롤백됐습니다. 시군구 단위 · 기본정보 100건 단위 커밋.

### 세법 · 실투자금

- `rate_formula` 를 엔진이 실제로 쓰게 했습니다. 지방세법 제11조 6억~9억 구간은
  세율이 구간 안에서 연속 변해서 표로 못 담습니다. `eval()` 대신 ast 화이트리스트로 제한 평가.
- 부대비용 규칙의 시도를 `lawd_cd` 에서 유도. 전에는 `region` 이 항상 None 이라
  지역이 적힌 중개보수 규칙이 **전부 걸러졌습니다.** 증상이 '미검증' 과 구분되지 않아
  `last_verified` 를 채워도 계속 '규칙 미입력' 으로 남았습니다.
- 토허 커버리지를 시도 단위로. 전에는 테이블이 전역으로 비었는지만 봐서,
  인천 자료만 넣으면 서울·경기도 '토허 아님' 으로 단정하고 전세보증금을 빼버렸습니다.

### UI (`apt_app.py`, 5001 포트)

```bash
.venv\Scripts\python apt_app.py     # http://localhost:5001
```

- `/` 순위 — **백테스트 학습 가중치가 없으면 잠깁니다.**
  `usefulness.load_weights` 가 값을 돌려주면 저절로 풀립니다. 사람이 푸는 스위치는 없습니다.
  배관 점검용 우회는 `?unlock=1` (화면 하단에 명시).
- `/search` 단지 검색 · `/complex/<id>` 대표가격 + 실투자금 · `/status` 데이터 현황 ·
  `/unmatched` 미매칭
- 디자인은 `pediatric-location-analyzer/app/ui/styles.css` 토큰을 가져왔습니다
  (Pretendard · 네이비/틸 · 8pt · 3단계 depth).
- DB 를 **읽기 전용**으로 엽니다. 수집 중에도 화면이 안 죽습니다.

## 남은 일 / 알려진 문제

1. **`collect rents --months 240`** — 아직 안 돌렸습니다. 매매 끝나고.
2. **수집기에 락 재시도가 없습니다.** 병렬 수집(시도별 3프로세스)으로 3배 빠르게 하려면
   `busy_timeout` 을 늘리고 재시도를 넣어야 합니다.
3. **대출 한도가 과대평가됩니다.** 규제지역 데이터가 미입력이라 LTV 규칙이 안 걸리고
   '집값' 이라는 산술 상한만 남습니다. 2.49억 아파트가 '필요 현금 0.04억' 으로 나옵니다.
   UI 는 '대출 없이 필요한 현금' 을 크게 쓰고 대출 반영값은 경고와 함께 작게 씁니다.
4. **전세 승계 + 주담대를 동시에 켜면 실투자금이 음수**가 됩니다. 각각의 최대치를 더합니다.
   전세 낀 집은 담보 여력이 없으니 현실에 없는 조합입니다. 지금은 UI 에서만 막고 있는데,
   엔진이 조합 자체를 거부하는 게 맞는지 판단이 필요합니다.
5. **농어촌특별세** 2건이 미검증입니다. 조문(0.2%)과 찾기쉬운생활법령 요약(취득세액×10%)이
   다르게 읽힙니다. 7.5억 120㎡ 기준 150만원 차이.
6. **[2026-09-04] 호재(catalyst_alpha) — 채점 경로가 처음부터 비어 있습니다.**
   순위 점수에 실제로 들어가는 건 `apt_engine/features/catalyst.py::load()` 인데,
   이게 읽는 `catalyst`·`catalyst_exposure`·`catalyst_state` 세 표가 전부 0행이고
   **채우는 CLI/import 도구가 아예 없습니다.** (오늘 낮에 만든 `cli catalyst build`는
   `future_catalyst`라는 **다른, 화면 표시 전용 표**를 채우는 것이라 순위에 영향이
   없습니다 — 헷갈리기 쉬운 이름이니 주의하세요.)

   섣불리 채우지 않은 이유 — `Catalyst Alpha = Economic Impact × Realization ×
   Time Relevance × Exposure × (1 − Priced In)` 인데, `economic_impact` 가
   `catalyst_state`에 **촉매 하나당 한 값**으로 박혀 있습니다. 이게 원 단위 절대
   금액이면 3억짜리와 15억짜리 단지가 같은 역 앞에 있어도 같은 금액을 받는다는
   뜻이라 이상하고, 그렇다고 %로 해석해도 그걸 각 단지 가격에 곱하는 코드가
   어디에도 없습니다. 이 설계가 뭘 의도했는지 코드만으로는 확정할 수 없었고,
   잘못 짐작해서 채우면 이후 모든 채점에 조용히 스며듭니다. 스키마 주석은
   "GTX 생기면 몇 % 오른다 같은 절대 상승률을 만들지 않는다 — 이미 개통된 노선의
   역세권/비역세권 가격비율 변화만 기록한다"고 못 박아뒀는데, 정확히 그 변환
   단계가 코드에 없습니다.

   오늘 밤 확보해둔 재료 — 최근 개통 4개 노선 15개 역(개통월 확인, `transit_analogue`
   실측 6건: 역세권/비역세권 가격비율이 개통 전후 −14.9%p~+5.2%p로 갈렸습니다,
   절반이 마이너스), 수도권 역 791개(운영중), GTX-B 사실관계(2025-08-04 착공,
   부평역 포함, 2030 목표 — [경인일보](https://www.kyeongin.com/article/1743824)),
   캠프마켓 공원화(아직 타당성조사 단계, 착공 전 — [경기일보](https://www.kyeonggi.com/article/20250827580235)).
   `economic_impact` 를 이 실측 델타로부터 어떻게 유도할지 결정하는 게 다음 작업의
   시작점입니다.

7. **[2026-09-04] 공급(supply) — 임포터 버그는 고쳤고, 실제 데이터가 필요합니다.**
   마이그레이션 014 가 `supply_plan.announced_ym`(§18 look-ahead 방지용 — "언제
   알았나") 칸을 만들었는데 `import_supply()` 가 그 칸을 한 번도 쓴 적이 없었다.
   `features/supply.py` 의 쿼리는 `announced_ym IS NOT NULL` 을 요구해서, 지금까지
   데이터를 넣어도 공급 feature 는 영원히 `DATA_MISSING` 이었다 — "데이터가
   없어서"가 아니라 "임포터가 애초에 못 채워서"였다.

   고쳤습니다: `announced_ym`을 CSV 서식에 추가했고, 비워두면 "분양은 관행적으로
   준공 30개월 전"이라는 통념으로 `move_in_ym`에서 역산합니다(추정이라 note에
   남습니다). 실측으로 `supply_ratio_2y`·`supply_cliff`가 `Status.OK`로 실제
   값을 내는 것까지 확인했습니다(전에는 항상 확인 불가).

   **남은 일**: 실제 수도권 입주예정물량 데이터가 아직 한 건도 없습니다(테스트
   행은 정리함). data.go.kr 을 검색했지만 "입주예정물량"을 딱 주는 공개 API를
   못 찾았습니다 — 한국부동산원 통계누리나 청약홈의 정기 발표 자료(보도자료·
   엑셀)를 받아 이 서식(`cli supply template`)에 맞게 넣는 수작업이 될 가능성이
   높습니다. 아실·부동산지인 같은 민간 집계는 출처로 쓰기엔 이 프로젝트의
   근거 기준에 못 미칩니다(정부 발표가 아님).

8. **[2026-09-04] 재건축 대지면적 — 다중 필지 합산이 필요합니다.**
   `apt_engine/collectors/landinfo.py` 는 좌표 하나를 역지오코딩해 **필지 하나**의
   면적만 가져옵니다. 대지권이 한 필지로 통합된 단지(은마 = 대치동 316 하나)는 맞는데,
   여러 필지에 걸친 단지는 대표 필지 하나만 잡혀 대지면적이 실제의 몇십 분의 일로
   나옵니다. 그대로 두면 용적률이 600% 같은 값이 되므로(실측 사례 있음),
   `MAX_PLAUSIBLE_FAR`(500%)·`MIN_LAND_PER_HOUSEHOLD` 로 걸러서 `land_area_m2`를
   NULL(확인 불가)로 둡니다.

   현재 도달 한계: 좌표 있는 단지 7,290개 중 5,280개(72%)만 대지면적 확보,
   2,010개는 이 문제로 못 채움(2026-09-04 재시도 결과 채움 0개 — 방법을 안 바꾸면
   더 안 늘어남).

   다음에 할 일: 좌표 근처의 연속지적도 필지를 **전부 조회해서 합산**해야 합니다.
   V-World 데이터 API(`LT_C_LANDINFOBASEMAP`)를 단지 건물 외곽선이나 반경으로
   여러 번 조회하는 방식이 될 것 같습니다. PNU 는 이미 `complex.pnu` 에 남아 있어서
   (걸러진 단지도 포함) 다시 지오코딩할 필요는 없습니다 — 그 PNU 를 기준으로 인접
   필지를 확장 탐색하면 됩니다.
