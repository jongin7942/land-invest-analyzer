**경기도 토지 공매 물건**을 수집해 "지을 수 있는 건물 기준의 적정 토지가" 대비 저평가된 물건을 찾아

### B-1. 특히 잘 되어 있는 것 (그대로 계승할 자산)

- **`app.jinja_env` 를 `build_static.py` 가 재사용**해 라이브/정적 두 형태를 하나의 템플릿으로 렌더링. `link_prefix`/`link_suffix`/`list_link`/`noindex` 를 전역으로 주입하는 방식이 깔끔하다. → PHASE 10 UX 인프라를 그대로 재사용.
- **`narrative.py` 의 설계 원칙** — "전부 규칙 기반(결정적)이며, DB에 저장된 필드 외 새 API 호출은 하지 않는다". 이게 요구사항 28(AI는 숫자를 만들지 않는다)의 정확한 구현 형태다. 아파트 리포트 생성기도 이 계약을 그대로 따라야 한다.
- **`raw_json` 원본 보관** — 필드 매핑이 바뀌어도 재파싱 가능.
- **`_pick()` 필드 후보 배열** — API 개편에 견디는 패턴. 아파트 API에도 그대로 적용.

## E. 현재 구조에서 위험한 부분

> 아파트로 확장할 때 **그대로 답습하면 안 되는** 것들. 요구사항 26(데이터 오류 방지)과 직결되는 항목을 ★로 표시.

### E-1. 기준선을 매 실행마다 전체 메모리 재계산 ★
`price_baseline.build_baselines()` 는 `land_trade` **전체 행**을 `SELECT` 해서 파이썬 dict 6개로 집계한다.
경기도 토지 3개월치(수천 행)는 문제없지만, 수도권 아파트 매매+전월세 5년치는 **200만~300만 행** 규모다.
`pipeline.py` 는 이걸 실행마다 다시 만든다. 메모리·시간 모두 감당 못 한다.
→ **집계는 SQL로 내리고, 결과를 `price_snapshot` 테이블에 영속화**해야 한다. 이건 요구사항 4(Historical Ratio)를 위해서도 어차피 필요하다.

### E-2. 인덱스·조회축 설계 부재
`land_trade` 인덱스는 `sgg_cd`, `deal_ymd` 2개뿐. 아파트의 핵심 조회축은 `(단지, 전용면적밴드, 거래일)` 이다.
SQLite 자체는 이 규모에서 아직 충분하지만(단일 사용자, 읽기 중심), **복합 인덱스와 WAL 모드는 필수**다.
Postgres 이관은 현 시점 오버킬 — 다만 스키마를 이관 가능한 형태로 설계한다.

### E-3. 수동 마이그레이션 방식의 한계
```python
new_cols = (("status","TEXT"), ("round","INTEGER"), ...)  # 손으로 추가
```
테이블 2개일 땐 되지만 20개 넘어가면 관리 불가. 그리고 컬럼 **삭제·타입변경·인덱스 변경**을 못 한다.
→ `PRAGMA user_version` 기반 순차 마이그레이션(`migrations/001_*.sql` …)으로 교체.

<a id="e-4"></a>
### E-4. 점수 산식이 단위가 다른 값을 그대로 더한다 ★★★ (가장 중요)
```python
score = ROAD_SCORE.get(grade, -5)      # 상수 ±40
if zoning in FAVORED_ZONING: score += 5 # 상수 +5
score += (uv["pct_below_median"] or 0)  # 퍼센트 (실측 98%까지 나옴)
```
**퍼센트와 임의 상수를 같은 축에서 덧셈**한다. 98% 저평가 물건 하나가 도로·용도 조건 전부를 압도한다.
실제로 코드 주석에도 "여주 계획관리 7,021평 임야가 98% 저평가로 나온다"는 사례가 적혀 있다.

요구사항 20은 "기본 100점 만점, 가중치 7개, 관리자 화면에서 변경 가능"이다.
**이 구조로는 가중치를 바꿔도 의미가 없다.** 각 팩터를 0~1로 정규화하는 계층이 반드시 먼저 있어야 한다.
→ `scoring/factors.py`(정규화) → `scoring/weights.py`(가중합) 2단 분리. 기존 산식을 아파트로 복사하지 말 것.

### E-5. `build_static.py` 가 `docs/` 를 통째로 삭제한다
```python
if DOCS_DIR.exists(): shutil.rmtree(DOCS_DIR)
```
- `docs/` 에 수동으로 넣은 파일은 다음 `publish.py` 실행에서 **전부 사라진다.** (이 분석 문서를 `docs_dev/` 에 둔 이유)
- 현재 이미 `docs/candidate/*.html` 약 500개가 git에 커밋돼 있다. 매 갱신마다 500개 파일이 전량 재작성 → **커밋마다 수백 파일 diff**, 리포지토리가 계속 비대해진다.

→ 정적 생성은 (a) 상위 N개만, (b) 데이터는 JSON 한 덩어리로 굽고 페이지는 클라이언트 렌더링(이미 `static_index.html` 이 이 방식), (c) `docs/` 를 git에서 빼고 GitHub Actions로 배포 — 셋 중 하나로 재설계.

### E-6. 데이터 조인이 문자열 추정에 의존한다 ★★
```python

    ...
    umd = f"{umd} {t[i]}"  # "양성면 노곡리" 형태로 조립
```

- 동일 이름 다른 단지 (래미안, 자이 등)

## F. 추천 DB 구조

### F-0. 설계 3원칙

1. **3계층 물리 분리** — `raw`(불변 원자료) / `derived`(재계산 가능한 파생) / `scenario`(가정 기반). [E-7](#e-7) 해결.
2. **전 테이블 공통 메타 컬럼** — 요구사항 25를 스키마 레벨에서 강제.
   ```
   raw     : source_id, retrieved_at, effective_date, confidence
   derived : engine_version, calculated_at, calc_trace(JSON), data_grade
   rule    : effective_from, effective_to, source_url, last_verified
   ```
   `data_grade ∈ {CONFIRMED, ESTIMATED, SCENARIO}` — 요구사항 14·25의 `● ◐ △` 표시가 여기서 나온다.
3. **단위 통일** — 금액 `원`(INTEGER), 면적 `㎡`(REAL), 비율 `0~1`(REAL). [E-16](#e-16) 해결.

### F-1. Layer 0 — 기준정보

| 테이블 | 핵심 컬럼 | 목적 |
|---|---|---|

| `region` | lawd_cd(5), bjd_cd(10), sido, sgg, emd, valid_from, valid_to | 서울·경기·인천 전체. **코드 개편 이력 보존**([E-12](#e-12)) |

### G-2. 엔진 계약 (모든 함수가 지켜야 할 규칙)

**1. 순수함수 — 엔진은 DB를 모른다**
```python
def acquisition_tax(price: int, house_count: int, area_m2: float,
                    is_regulated: bool, *, as_of: date, rules: TaxRuleSet) -> Calc:
```
DB 조회는 `repo/` 가 하고 엔진에는 **값으로 주입**한다. 테스트가 쉬워지고(요구사항 34), 규칙 버전을 갈아끼울 수 있다.

**2. `as_of` 를 모든 규칙 조회의 필수 키워드 인자로 (기본값 금지)**
```python
def permit_zone_at(complex_id, *, as_of: date, scope: Scope) -> PermitStatus:
```
기본값을 `date.today()` 로 두지 **않는다.** 호출부가 반드시 명시하게 강제.
→ 요구사항 26-7(기간 만료), 26-11(세법 기준연도), 26-8(내·외국인)을 **타입 레벨에서 차단**.

**3. 모든 엔진 함수는 `Calc` 를 반환한다**
```python
@dataclass(frozen=True)
class Calc:
    value: float | int
    inputs: dict          # 입력값
    formula: str          # 계산식(사람이 읽는 문자열)
    intermediates: dict   # 중간값
    evidence: list[dict]  # 근거 (source_id, url, 원문 인용)
    grade: Literal["CONFIRMED", "ESTIMATED", "SCENARIO"]
```
이게 요구사항의 **"입력값 → 계산식 → 결과값 → 근거 추적 가능"** 을 구조로 만든 것이다.
`calc_trace` 컬럼에 이 객체를 직렬화해 저장한다. [E-8](#e-8) 해결.

**4. 단위는 원(int)·㎡(float)·비율(0~1) 단일계**
`units.py` 에 `Won = NewType('Won', int)` 같은 타입 별칭 + `to_eok()`/`to_manwon()` 표시 함수만 둔다.
엔진 내부에서 억·만원이 등장하면 리뷰에서 반려. [E-16](#e-16) 해결.

**5. LLM은 `engine/` 밖에만 존재한다**
요구사항 28의 6가지 AI 역할(비교단지 선정 제안, 가격격차 설명, 촉매 설명, 시나리오 생성, 리스크 설명, 리포트 작성)은
전부 `narrative/` 또는 `relative/benchmark.py` 의 **후보 제안** 단계에만 들어간다.
LLM이 제안한 것도 `benchmark_relation.is_manual=false` + `selection_reason_json` 으로 저장되고,
**가격·세금·대출·거래량·토허·용적률 숫자는 절대 LLM이 만들지 않는다.**

**6. 외부 의존성 최소 유지**
현재 3개(`requests`, `python-dotenv`, `flask`)를 지킨다. 추가는 `pytest` 정도.
- IRR: `numpy-financial` 대신 **이분법 직접 구현** (부호 변화 구간 탐색 + 이분 수렴). CF가 다중 부호변화면 IRR이 복수해가 되므로 **MIRR 병기 또는 경고**.
- 집계: `pandas` 대신 **SQL 집계**. [E-1](#e-1) 해결과 같은 방향.

### G-3. 요구사항 30(목표수익률 역산)의 구현

이게 "가장 중요한 기능"이라 하셨으므로 설계를 명시한다.

```
buy_price_max(target_irr, holding_years, future_price, cf_template, tax_rules, loan_rules)
  = 이분법으로 매수가 P 를 탐색:
      P → Initial Equity(P) → 취득세(P) → 보유세(공시가격 f(P)) 
        → 양도세(매도가 - P - 필요경비, 보유·거주기간)
        → CF 재생성 → 세후 IRR(P)
      세후 IRR(P) = target_irr 을 만족하는 P
```
**핵심: 매수가가 바뀌면 취득세·보유세·양도세가 전부 따라 바뀌므로 단순 역산이 불가능하다.**
CF 전체를 P의 함수로 재구성한 뒤 이분법으로 푸는 게 유일하게 정확한 방법이다.
→ `cashflow/builder.py` 를 **P를 인자로 받는 순수함수**로 설계하는 것이 이 기능의 전제조건이다.
PHASE 7 설계 시점에 이걸 염두에 두지 않으면 PHASE 후반에 전면 재작성이 필요해진다.

## H. 추천 개발 순서

### H-1. 제안하신 순서에 대한 3가지 조정 의견

**조정 1 — PHASE 0(기반) 신설 (필수)**
테스트 프레임워크·마이그레이션 체계·`Calc` 트레이스 규약·단위 통일이 없으면
요구사항 25(신뢰도)·26(오류방지)·34(테스트)를 **나중에 붙일 수 없다.** 스키마와 함수 시그니처에 녹아야 하는 것들이다.
예상 1~2일. 이걸 건너뛰면 PHASE 5쯤에서 전면 재작성이 발생한다.

**조정 2 — PHASE 2 ↔ PHASE 3 상호의존 해소**
제안하신 PHASE 2는 "현재가격/전세/실투자금"인데, **Initial Equity를 계산하려면 PHASE 3이 먼저 필요**하다:
- Initial Equity = 매매가 − 승계 전세보증금 + **취득세**(← PHASE 3) + 중개보수 + 법무비
- 그런데 요구사항 10 마지막: **"토허 때문에 전세를 활용할 수 없다면 전세보증금을 차감하면 안 된다"** (← PHASE 3)

→ 권장 순서:
- **PHASE 2**: 대표가격(매매) + 대표전세가 + 전세가율 **까지만**
- **PHASE 3**: 토허 / 규제지역 / 대출 / 세금 규칙 테이블 + 취득세
- **PHASE 3.5**: Initial Equity (= 2 + 3 결합). 여기서 처음으로 "실투자금"이 나온다

**조정 3 — 재건축(PHASE 6)은 2단계 스크리닝으로**
수도권 1,000세대 이상 단지는 대략 **1,500~2,500개**다. 정비계획 용적률·대지지분·조합원수·공사비는
**API가 없어 사실상 수기 데이터**다. 전 단지를 채우는 건 불가능하다.

→ 2단계 구조:
- **1차(자동)**: 사용승인 30년 이상 + 현재 용적률 200% 이하 + 평균 대지지분 큰 순 → 후보 자동 스크리닝
- **2차(수기)**: 상위 50~100개만 정비사업 데이터를 채워 정밀 분석
- 나머지는 `data_grade='ESTIMATED'` 로 표시하고 **정밀 숫자를 내놓지 않는다** (요구사항 14의 "정확한 데이터가 없으면 정확한 숫자인 것처럼 보여주지 않는다")

| **4** | 가격사다리 / 벤치마크 / Current·Historical Ratio | `ladder_axis`/`benchmark_relation`/`ratio_norm` | 선정근거 NOT NULL 테스트, 비율 재현성 |
| **5** | GTX 선행사례 / 공급 / 촉매 / Future Reasonable Ratio | `transit_analogue`/`future_catalyst` | 근거 없는 촉매 저장 시 실패하는 테스트, 26-10 |
| **6** | 재건축 사업성 (2단계 스크리닝) | `redevelopment_project`/`redevelopment_scenario` + 신축전환원가 | 비례율·분담금 손계산 대조, data_grade 표시 |
| **7** | Cash Flow + Peak Equity + 세전/세후 IRR | `cash_flow`/`investment_result` | 손계산 IRR 대조, Peak Equity 타임라인 테스트 |
| **8** | 정규화 + 가중치 + Risk Score + 8종 랭킹 + 현금구간 TOP10 | `score_weight` + 랭킹 API | 가중치 변경이 순위를 실제로 바꾸는지 테스트 |
| **9** | 사용자 프로필 맞춤 필터 + **Buy Price 역산** | `user_profile` + `buy_price_max` | 목표 IRR 역산 왕복 검증(P → IRR → P) |
| **10** | 결과화면 / 상세리포트 / 신뢰도 아이콘 / 카톡·정적배포 | 템플릿 + `narrative/report.py` | 기존 토지 사이트 무영향, 정적 생성 규모 대응 |

각 PHASE 종료 시 **기존 토지 프로그램 회귀 테스트**를 돌린다(`main.py --stats`, `pipeline.py --top`, `app.py` 기동, `build_static.py`).

## I. 각 PHASE 예상 난이도

난이도는 **코드 복잡도가 아니라 "데이터 확보 가능성 + 검증 가능성"** 기준이다.

| PHASE | 난이도 | 주된 어려움 | 예상 공수 | 최대 리스크 |
|---|:---:|---|---|---|
| 0. 기반 | **하** | 없음. 다만 생략 유혹이 큼 | 1~2일 | 생략하면 PHASE 5에서 전면 재작성 |
| 1. 수집+매칭+검증 | **중상** | ★ **단지명 매칭**([E-6](#e-6))이 공수의 절반. API 호출 시간(하룻밤) | 4~7일 | 매칭 실패율이 높으면 이후 전부 오염 |
| 2. 대표가격 | **중** | 로직은 단순. **이상치 규칙 정의**가 실전 난이도(무엇이 "특수층"인가) | 2~3일 | 규칙이 과하면 표본이 사라짐 |
| 3. 토허·규제·대출·세금 | **최상** | ★ **데이터가 API로 안 나온다**(전부 수기) + 세법 복잡도 + 자주 바뀜 | 7~14일 | **프로젝트 최대 리스크.** 양도세·종부세는 예외규정이 매우 많음 |
| 3.5. Initial Equity | **하** | 2+3 결합만 | 1일 | — |
| 4. 상대가치·비율 | **중상** | 계산은 쉬움. **벤치마크 선정 기준 설계**가 본질 | 3~5일 | 자의적 선정 → 결과 신뢰도 붕괴 |
| 5. GTX·촉매 | **상** | 선행사례 표본이 적어(GTX-A 개통 구간뿐) **통계적 타당성 확보가 어렵다** | 4~7일 | 과적합. "GTX면 몇 % 상승" 유혹 |
| 6. 재건축 사업성 | **최상** | ★ **대지지분·정비계획 용적률·공사비 API 없음.** 단지별 수기 | 7~14일 | 전 단지 커버 불가 → 2단계 스크리닝 필수 |
| 7. CF + IRR | **중** | 계산은 표준. 세금 엔진 의존. **P의 함수로 설계**해야 PHASE 9가 가능 | 3~5일 | 설계 실수 시 PHASE 9 재작성 |
| 8. 랭킹 | **하~중** | 정규화 설계만 제대로 하면 쉬움 | 2~3일 | [E-4](#e-4) 답습 시 무의미한 점수 |
| 9. 맞춤 + Buy Price 역산 | **중** | 이분법 수렴. 세금이 P에 의존해 비선형 | 3~4일 | 수렴 실패 케이스 처리 |
| 10. 리포트 / UX | **중** | 기존 자산 재사용 가능. **정적 생성 규모**([E-5](#e-5)) 재설계 필요 | 4~7일 | 페이지 수 폭증 |

**총 예상: 40~80일 (1인 기준)**. PHASE 3과 6이 전체의 40% 가까이를 차지한다.

### I-1. 솔직한 리스크 평가

1. **PHASE 3(세금·토허·규제)이 이 프로젝트의 성패를 가른다.**
   나머지 29개 요구사항이 완벽해도 세금이 틀리면 세후 IRR·Buy Price가 전부 틀린다.
   그런데 이 영역은 API가 없고, 법이 자주 바뀌고, 예외규정이 매우 많다.
   → **처음부터 전 케이스를 커버하려 하지 말고**, 대상을 좁혀 정확도를 확보할 것을 강력히 권한다:
   *"1세대 1주택 / 조정대상지역 여부 / 보유·거주기간"* 조합만 먼저 정확히 → 나머지는 "판정 불가" 표시.
   요구사항 25의 정신("추정치를 확정값처럼 표시하지 말 것")이 여기에 가장 절실하다.

2. **양도세·1세대1주택 비과세는 개인 세무 판단 영역이다.**
   프로그램 결과는 반드시 `ESTIMATED` 로 표시하고 "실제 신고 전 세무사 확인" 문구를 상시 노출해야 한다.
   기존 `due_diligence.py` 가 이미 이 태도를 취하고 있다 — 그대로 계승.

3. **PHASE 6(재건축) 전 단지 커버는 불가능하다.** 2단계 스크리닝으로 범위를 좁히는 것이 유일한 현실적 해법.

4. **PHASE 5의 GTX 선행사례는 표본이 근본적으로 부족하다.**
   GTX-A 수서~동탄/운정~서울역 구간이 사실상 유일한 관측치다.
   → 신분당선 연장, 9호선 연장, SRT 개통 등 **과거 광역철도 개통 사례로 표본을 확대**하는 설계를 권한다.
   그래도 "확정 예측"이 아니라 "참고 범위"로만 제시해야 한다.
